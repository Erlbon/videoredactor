## 2026-11-26#02 -- Delete Files (Recycle Bin) and the Delete key asks what you mean

- **New: File > Delete Files (Recycle Bin)** (Shift+Delete). It sends the selected video files to the Recycle Bin (recoverable) after a Yes/No question, takes them off the list, and says how many went in the status bar. Only the video file is deleted: subtitles, posters and .nfo files next to it stay. A video with unsaved changes is refused (nothing is deleted until you save or deselect it). If the player has the file open, the player is closed first. On a drive without a Recycle Bin (network share, USB disk) the file goes to the Library safety backup folder; with none set, the file is kept and the reason is shown. It is also in the right-click menu of the list.
- **The Delete key asks: Remove from List, Delete Files (Recycle Bin) or Cancel.** Before, Delete only took the video off the list and left the file on disk, which is not what most people expect. Remove from List is the default button, so Delete then Enter never deletes a file. Choosing Delete Files sends the files to the Recycle Bin at once (no second question). The File menu items Remove from List and Delete Files still act at once.

## 2026-11-26#01 -- Check for Updates installs the new version itself; a Windows installer -- redactor_common 2026-11-26-02

- **Help > Check for Updates installs the update** instead of only opening the download page. The app is on the
  Redactor family's update framework (redactor_common docs/update-framework.md): every release carries an
  `update-manifest.json` naming each download with its size and checksum, and every copy says how it was put on the
  PC. The portable `videoredactor.exe` replaces itself (the old one is kept as `videoredactor.exe.old` until the next
  start) and starts again; an installed copy runs the new installer silently and starts again. When it cannot update,
  it says why, with a Copy details button, and still offers the download page.
- **A Windows installer**, `videoredactor-setup.exe`: per user, no administrator rights, into
  `%LOCALAPPDATA%\Programs\The Video Redactor`, with a Start menu entry. The one-file `videoredactor.exe` stays the
  portable download. Neither bundles ffmpeg or MKVToolNix (put them in `tools\` beside the exe, on PATH, or name
  them in Preferences).
- **A copy on an older version must be updated by hand once**: download this release from the release page. Its
  Check for Updates cannot read the new releases' manifest (decided for the whole family: no bridge for old copies).
- The command line has `videoredactor --check-update [--release-tag vX]` (prints what this copy would do, as JSON;
  changes nothing) and `--update` (does it without a window), for the release gate. `videoredactor notes PATH
  --update` is still the notes command's own option.
- Releases are now made with redactor_common's release tool (`pyproject.toml`), which builds the exe, the installer
  and the manifest, publishes a pre-release, checks the update from the previous release, and only then makes it
  Latest. The GitHub workflow no longer builds the Windows exe (its upload would replace the file the manifest
  pins); it adds only the Linux download, when the release is published. The Linux build cannot replace itself: it
  says so and opens the release page.
- Shared code moved from redactor_common 2026-11-21-02 to 2026-11-26-02. For this app: `%dummy%` in an Import
  Metadata from Filename pattern skips a piece of text (and may be used more than once). The rest is MusicBrainz and
  Discogs lookups, which this app does not use, and the Delete key's new question, which applies only to apps with
  Delete Files.

## 2026-11-18#04 -- conversion: the homeserver3 gaps (decisions 9-18)

The owner's answers on the conversion decision page of 2026-11-18, compared with his homeserver3 scripts.

- **Several files at once.** Preferences > Conversion has "Remuxes at once" (default 4) and "Re-encodes at once"
  (default 2). The progress dialog names the files that are running, and Cancel stops them all.
- **The dry run is a table.** It shows each file's route (Remux, Shrink, Re-encode or Skip), resolution, codec,
  video Mb/s and action. It can be sorted, and "Only files that would change" hides the rest. Untick the files to
  leave out, and "Convert the ticked files" converts the rest for real, with the same choices. "Copy the report"
  copies the old text lines.
- **New column: Would convert** (hidden at first; switch it on from the header menu). It shows "-> 720p",
  "re-encode", "remux" or "no" for each row, judged by the same rules, and can be filtered. It is an estimate
  from the table's own data: a remux that one of an MP4/MKV's streams needs shows up in the dry run only.
- **The space saved.** The end report says "X GB -> Y GB, saved Z GB (N%)", and each file's line gives its
  sizes before and after. The Redact convert step reports the sizes too.
- **When a shrink fails, the next try follows the fallback chain of his scripts.** First the GPU decode with the
  audio copied, then the GPU decode with the audio as AAC 192k, then the same two with the CPU decoding. The GPU
  steps are only used with "GPU decode" on. The encoder does not change. The report says which step worked.
- **Lenient mode for damaged files**, a tick in Media > Convert, off by default. ffmpeg ignores decode errors and
  drops broken packets. A result that passes every check except its length, and is at least 60% as long as the
  original, is kept as `<name>.partial.mkv/.mp4` beside the original. It never replaces the original. The report
  gives both lengths.
- **"Scale music videos to 1080p HEVC"**, a tick in Media > Convert for this run only. Without it, music videos
  follow their own rule (decided 18 Nov): 4K is kept, and a music video above 1440p is re-encoded at its own size
  only above 25 Mb/s (H.264) or 35 Mb/s (HEVC, VP9, AV1). Both limits are in Preferences > Conversion. Below 4K,
  music videos are left alone.
- **Highest resolution kept, per content type** (Preferences > Conversion). Series use the "scale down to" height
  (720p) as before. Movies, and Clip/Misc/Porn/untyped files, have "No limit" by default. A file is still only
  re-encoded when the bitrate rule says it is too big. A file of a kind with no limit, or one already within its
  limit, is re-encoded at its own size instead of being scaled to 720p. The rules still apply to movies only with
  "apply to movies" on.
- **x265 preset setting** (default medium). Both libx265 uses follow it: the legacy re-encode and the software
  shrink.
- **Old video the app does not know**, in a legacy container (AVI, WMV, RM, FLV...), is now re-encoded with x265
  CRF 23 and AAC 160k, as his script does. Before, it was skipped. An unknown codec inside an MP4 or MKV is still
  left alone.
- **Fix: subtitle streams without a codec name** (teletext or closed-caption placeholders) are no longer mapped
  into the result, where ffmpeg aborted on them, and the verify step no longer counts them. This is his
  conversion prompt's own rule.

## 2026-11-18#03 -- lookups follow the Content Type; Show adult content

- **The Look Up menu shows only the lookups that fit the selected files' Content Type** (the owner's decisions
  of 2026-11-18). The others are hidden, and their shortcuts do nothing, the way Get Lyrics already worked. The
  same goes for the row right-click menu and Get Poster.
  - TMDB (Movie): Movie and Porn.
  - TMDB (TV Show) and TheTVDB: TV.
  - IMDb (Local Database): Movie, TV and Music Video.
  - ThePornDB and StashDB: Porn.
  - Get Poster: Movie, TV and Porn.
  - Get Lyrics and Get Cover: one Music Video, as before.
  - Subtitles: every type.

  A file with no Content Type yet fits every lookup. When several files are selected, a lookup is shown only if
  it fits every one of them.
- **Redact's "Look up metadata" step follows the Content Type when it is set.** Movie is looked up as a movie and
  TV as a TV show, whatever the filename looks like. Music Video, Porn, Clip and Misc are not looked up there, so
  a music video named "Artist - Song (1990)" no longer comes back with a film. A file with no type still goes by
  its filename, as before. "Fill from ThePornDB/StashDB" now asks only about Porn files and files with no type.
- **New: Tools > Preferences > Adult Content > Show adult content.** Off hides the Porn content type, the ThePornDB
  and StashDB lookups and API keys, Tools > Porn Tags, and the Redact step that asks those services. That step is
  still listed in the recipe, but it does nothing and says why. A file already tagged Porn keeps its tags and
  still shows Porn as its type. Until you set the switch, it is on if a ThePornDB or StashDB key is saved, and off
  otherwise, so nobody loses the lookups they use. This replaces splitting the adult features into an app of
  their own.
- **New field: Collected from**, on every Content Type. It records where this copy of the video came from. A
  pick list gives the kind: YouTube, Vimeo, Other website, TV broadcast, DVD, Blu-ray, LaserDisc, VHS, CD-ROM /
  Enhanced CD or Unknown. A detail line holds the rest: the link, the channel and year, or the disc's name. In the
  side panel they are two rows, "Collected from" and "Collected from (detail)". The table has both as columns, and
  the kind gets a value filter. They are stored as COLLECTED_FROM and COLLECTED_FROM_DETAIL (MKV tags, and
  freeform atoms in MP4), apart from the "Source link", which still names the record a lookup matched. On the
  command line they are `collected_from` (alias `source`) and `collected_from_detail`. `collected_from` takes only
  the pick-list values.
- **Collected from is suggested from the file's web address.** When the field is empty and the Comment (or the
  Description) holds a web address, as yt-dlp writes it, the panel fills in YouTube, Vimeo or Other website with
  that link and says it is a suggestion. It is written only when the file is saved, the same as a Content Type
  read from an MP4's media type. A new Redact step, "Fill Collected from from the file's web address", does the
  same for many files: it is off by default, and its results always go to Needs review.
- IMVDb (music video credits) is not added yet: its API search is shut down for now. It will be looked at again
  when search is back.

## 2026-11-07#01 -- lyrics as a subtitle track, and a cover for music videos

- **Get Lyrics can embed the timed lyrics in the video as a subtitle track.** Tick "Also embed the timed lyrics in
  the video as a subtitle track" and the file gets a track named "Lyrics" right away, in the language and with the
  offset chosen in the dialog. Nothing is re-encoded. An MKV goes through mkvmerge, which keeps every track, tag,
  chapter and attachment as they are. An MP4 goes through ffmpeg (as a mov_text track), and its tags and poster are
  written back before the result is checked. The new file is checked before it takes the old one's name: the same
  video and audio, one more subtitle track, the same length. The original goes where Library safety sends replaced
  files (the Recycle Bin, or the quarantine folder). Embedding again replaces the Lyrics track instead of adding a
  second one. The track is the default subtitle only when the video has no other subtitle track. Tags you have not
  saved yet stay staged.
- **Metadata > Look Up > Get Cover (iTunes, MusicBrainz, Discogs)** finds a cover for one Music Video by its artist
  and song title. It searches iTunes (1000 x 1000 artwork, no key), MusicBrainz with the Cover Art Archive (no key;
  official singles and albums first, live recordings and bootlegs last) and Discogs (only with a Discogs token,
  which is new in Tools > API Keys; a token saved in mp3redactor works here too). The covers are shown side by side
  with the current poster. The one you pick is staged as the poster through the usual review: Save All embeds it,
  Undo takes it back. A music video's cover is square release artwork (at least 400 x 400), so it gets its own rule
  next to the portrait-poster rule, which is unchanged.

## 2026-11-05#02 -- tests that only passed on this machine

No change to the app. GitHub's Windows test run had failed since 2026-10-15 on three tests, and the Release build would have hit a fourth:
- **The Cyrillic lyrics test** read ffprobe's output in the system's text encoding. Python 3.15 uses UTF-8 by
  default; the 3.12 on GitHub uses cp1252, which garbled the text. The test now reads it as UTF-8, as the app's own
  ffmpeg calls already do.
- **The two audio-only damage tests** looked for at least 1 KB of audio with no video in between. In the 30 fps
  sample, that existed only by luck of one ffmpeg build: GitHub's ffmpeg 9.0.2 never puts more than 0.93 KB of
  audio between two frames. These two tests now use a 10 fps sample, which has about 2.7 KB between frames on any
  build.
- **The read-only tests skip when run as root.** The Release workflow's Linux build runs the tests as root in
  Docker, and root can write a read-only file (mp3redactor's last releases lost their Linux download to this).
