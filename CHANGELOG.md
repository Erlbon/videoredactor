## 2026-09-03#08 — Three new Operations commands: Case Conversion, Search/Replace, Auto-Numbering

Requested directly. Added under Operations, after Remux and Rename/Export by Pattern, separated by a divider since these three are a genuinely different category (metadata field text transforms, not file-level operations).

New `core/text_transforms.py` holds all the actual transformation logic, kept deliberately separate from the three new dialogs so it's fully testable without PyQt6 -- 33 new tests, more thorough than the initial implementation needed to be, because a real bug turned up while testing it:

**Case Conversion** offers UPPERCASE, lowercase, Title Case, and Sentence case. Deliberately NOT built on Python's `str.title()`, which has a well-known bug mangling apostrophes (`"don't stop".title()` gives `"Don'T Stop"`) -- implemented a proper word-boundary-aware capitalizer instead. Small words (a, the, of, in, etc.) stay lowercase in Title Case unless they're the first or last word -- and, caught while testing against realistic movie/show titles rather than toy examples, unless they immediately follow a colon or dash. The first version of this only checked "first or last word of the whole string," which gave "Star Wars: a New Hope" instead of the correct "Star Wars: A New Hope" -- an extremely common pattern for exactly the kind of titles this app deals with, so this was worth getting right rather than shipping a known-wrong edge case.

**Search/Replace** does plain substring replacement, not regex, with a case-sensitivity toggle -- explicitly not regex, both to keep the tool simple and to avoid the failure modes an invalid user-supplied pattern could cause. Special characters in the search text (`.`, `(`, etc.) are escaped internally before the case-insensitive path's regex is built, so they're always matched as literal text regardless of which mode is active, never accidentally interpreted as regex syntax.

**Auto-Numbering** assigns a sequential number (configurable start, increment, and zero-padding) to a chosen field, in the current selection/table order -- no separate sort imposed, matching how Rename by Pattern and Import Metadata from Filename already behave. Two modes depending on the field's type: numeric fields (Season #, Episode #, Personal Rating) get the number written directly; text fields (Title, Track Title, etc.) get it prefixed onto their existing value with a configurable separator ("Pilot" → "01 - Pilot"), so existing content isn't clobbered. New `TEXT_FIELDS`/`NUMERIC_FIELDS` lists in `core/video_metadata.py` classify which of the existing editable fields are eligible for which mode -- deliberately excluding `content_type` (a fixed enum), `genre_tags`/`language` (controlled-vocabulary fields, where a case or substring change could break matching against the picker's own option list), and `release_date` (a date format, not free text).

All three dialogs follow the same shape already established by Rename by Pattern and Import Metadata from Filename: a live preview table, an Apply button that stages changes onto `vf.metadata` and marks `vf.dirty = True` without saving to disk, and the same selection-or-all-loaded-files scope. Each dialog reuses `gui/tag_panel.py`'s own `FIELD_LABELS` for field names in its dropdowns rather than a second copy that could drift out of sync -- an early draft of the Case Conversion dialog duplicated a small local label dict before this was caught and fixed during review, the same mistake the placeholder reference list explicitly avoided a few entries back.

Deliberately did not add keyboard shortcuts to these three -- unlike the previous entry's shortcuts (added to commands with an established, obviously-high usage pattern), these are brand new and haven't earned that judgment yet.

Added a new Stage 12 to `FIRST_BUILD_TEST_PLAN.md` covering all three dialogs, including a specific check for the colon-capitalization fix, the apostrophe fix, and the negative-number-padding edge case.

280 total tests now passing (was 247 before this entry -- 33 new, all in `tests/test_text_transforms.py`).

## 2026-09-03#02 — Fourth real MKV bug report: the diagnostic finally paid off — this is a READ bug, not a write bug

The user's fourth screenshot on this saga was the most useful one yet, precisely because the diagnostic enrichment from the previous entry worked as designed. The save_error's `tool output:` section showed mkvpropedit's own text: "The file is being analyzed. / The changes are written to the file. / Done." -- mkvpropedit's OWN confirmation that the write genuinely succeeded. This flips the entire investigation: three previous entries all assumed the bug was somewhere in the write path. It never was. It's in the read path.

Two real, confirmed problems in `read_mkv_metadata()`, both found by re-reading the function with this new information in hand: `mkvextract`'s stderr was being silently discarded completely -- never even inspected, regardless of outcome -- and the code relied on an unverified assumption that `mkvextract <file> tags` (called with no output argument) defaults to printing its XML to stdout. Neither assumption had ever been confirmed against a real mkvextract binary.

**Fix 1**: `read_mkv_metadata()` now asks mkvextract to write to an explicit temp output file (`mkvextract <file> tags <output-path>`) instead of relying on the unconfirmed stdout default -- this removes that specific ambiguity entirely, regardless of which convention mkvextract's tags mode actually follows. Falls back to reading stdout if the expected output file was never created, in case this assumption is also wrong for some mkvextract version.

**Fix 2**: `read_mkv_metadata()` gained an optional `diagnostics` dict parameter that captures mkvmerge's and mkvextract's raw stderr (previously thrown away entirely, in both cases). `VideoFile._verify_write()` now passes this through and includes it under a new `read-back tool output:` section in the save_error when a mismatch is found, alongside the existing write-side `tool output:` section from the previous entry.

Caught and fixed a real bug in my own first draft of the error-message change, via a test that failed exactly as it should have: initially surfaced `mkvextract_stdout` (the routine extracted XML content itself, or empty in the normal explicit-file-write case) alongside `stderr` in the "diagnostic" text -- which is noise, not signal, since stdout in the success case is just the data, not an error report. Fixed to only surface `*_stderr` keys, never stdout.

Also caught and fixed a genuine syntax error introduced during the edit itself: a duplicated function signature and opening docstring paragraph left over from an imprecise `str_replace` match, which would have made the whole module fail to import. Caught by the routine `py_compile` check before it ever reached a test run, let alone a shipped build.

Verified for real: the explicit-output-file mechanism correctly reads from the temp file when mkvextract writes there; the stdout fallback still works if the file is never created; the temp file is cleaned up after every read, matching the same no-leaked-files standard already applied to the write side's own temp file; `diagnostics` correctly captures both mkvmerge's and mkvextract's stderr text when either tool fails; the default (`diagnostics=None`) case still works for every other caller that doesn't care about it; and a full simulated reproduction of the user's exact scenario -- mkvpropedit confirming success while mkvextract fails with a genuine error -- now produces a save_error containing both the write confirmation AND the read failure's exact stderr text. 7 new tests: 6 in `tests/test_mkv_tags_xml.py`, 1 in `tests/test_save_verification.py`.

**This is genuinely the most information-dense diagnostic this project has ever shipped for this bug.** If the fix itself is still wrong, the next report should at minimum contain mkvextract's own error text verbatim -- which is very likely the actual root cause, not something requiring a fifth guess.

## 2026-09-02#21 — Third real MKV tag bug: split mkvpropedit invocations + verify now reports every mismatch, not just the first

The user's earlier "no tags are written to MKV files" report turned out to need TWO fixes, not one -- this is the second, confirmed by the app's own verify-after-write safety net catching a real save failure and showing it in a screenshot: `content_type` was set to TV, but the file read back UNSET, even after the `global`/`all` mkvpropedit keyword fix from the previous entry.

**`write_mkv_metadata()` previously combined `--edit info --set title=...` and `--tags global:...` into ONE mkvpropedit invocation**, on an assumption about safely combining actions that was never confirmed against a real binary. Split into two separate, single-purpose invocations -- title first, then tags -- removing that specific unverified assumption from the picture entirely. Results are combined into one `CompletedProcess`-shaped return (worse of the two return codes, concatenated stdout/stderr) so callers didn't need structural changes. This costs one extra process launch when both title and tags need writing, an accepted tradeoff for narrowing down what's actually happening.

**`_verify_write()` previously stopped at the FIRST mismatched field.** Since `content_type` now sorts first in `EDITABLE_FIELDS` (moved there in the "Content Type first" panel-ordering change a few entries back), this meant the verification could only ever confirm ONE broken field even if others -- genre_tags, season_number, whatever else was set -- were also silently failing alongside it, hiding the true scope of the problem from whoever's trying to diagnose it next. Now reports every mismatch found, together, in one message.

**Also now captured: the write call's raw stdout/stderr, even on nominal success**, appended to the verification failure message when present. A tool can print a warning while still exiting 0, and that text was previously discarded entirely just because the exit code looked fine -- it's now included, since it could be exactly the detail that finally reveals the real root cause.

Verified for real: confirmed two genuinely separate `subprocess.run` calls happen when both title and tags are set (not one call with combined arguments), confirmed each invocation only contains its own relevant arguments (no cross-contamination), confirmed the combined result's returncode is only 0 if BOTH calls succeeded, confirmed stdout from both calls is concatenated rather than one overwriting the other, and confirmed a simulated multi-field failure (content_type, season_number, and genre_tags all silently not persisting at once) now produces one message naming all three instead of just the first. 8 new tests: 5 in `tests/test_mkv_tags_xml.py` for the split-invocation behavior, 3 in `tests/test_save_verification.py` for the richer multi-mismatch-plus-tool-output message.

Updated the two existing tests that asserted the old "one combined call" behavior to match the new split-call reality, and updated `FIRST_BUILD_TEST_PLAN.md`'s Stage 3 to explain what changed and why this fix is now the most important thing to verify -- if tags still don't persist after this, the full save_error message should at minimum show every affected field together and possibly mkvpropedit's own diagnostic text, giving a real lead instead of another guess.

## 2026-09-02#19 — Save-verification safety net + third real MP4 custom-field fix

User confirmed the "no MKV tags written" report was on build #17 (already includes the earlier MKV `global`/`all` keyword fix), and separately reported that only Title persists across saves in general -- content_type and season numbers revert on reload, tested via a real screenshot showing Status = OK (not SAVE FAILED) both before and after closing the app. A write that reports success while silently not persisting is a serious class of bug on its own, so this entry does two things: closes the honesty gap first, then applies a third concrete fix.

**`VideoFile.save()` now verifies every write against an immediate re-read.** After a successful write call (no exception, mkvpropedit returncode 0), the file is read straight back and compared field-by-field against what was just written -- only fields that were actually non-empty in the in-memory metadata are checked, so an intentionally-unset field reading back empty is correctly treated as agreement, not a mismatch. Any disagreement produces a specific, actionable `save_error` naming the exact field and both the expected and actual values, and `dirty` correctly stays `True` so the row doesn't misleadingly show as saved. This makes the entire class of "write claims success but data silently vanishes" bug impossible to pass through as a false OK status, regardless of whatever the underlying backend cause turns out to be -- verified against a simulated reproduction of the exact reported symptom (mkvpropedit returns 0, but a re-read shows the custom tags never actually landed) and against the inverse case (a genuine successful write must NOT be flagged as a false positive). ## 2026-09-02#03 — Column drag/reorder, visibility toggle, and controlled vocabulary for Genre/Language

Three requested features, matching the epub tool's own table-column and mp3tag-inspired UX:

**Column drag-and-drop reordering** — `QHeaderView.setSectionsMovable(True)`, Qt's built-in support, requiring no custom drag logic. Row-to-file lookups (`VideoFile` via `Qt.UserRole`) are unaffected by visual reordering since they key off the *logical* column index, which never changes when a column is dragged -- only its on-screen position does.

**Column visibility toggle** — right-click a column header for a checklist of every current candidate column (per the active Content Type filter). `filename` is deliberately never offered here -- it's the row-identity anchor every lookup depends on.

**Persistence** — column order, hidden-column set, and per-column widths all save to `settings.ini` under `[table]`, surviving both app restarts and Content Type filter changes. The filter decides the *candidate* column set; the user's saved preferences decide their order and which of those candidates actually show. Business logic (merging a persisted order onto a new candidate set, visibility rules, the `filename`-is-always-protected rule) lives in `core/table_settings.py`, fully unit-tested (12 tests) rather than embedded in untestable GUI code -- same testable-core-plus-thin-GUI-wiring pattern used throughout this project.

Caught one real subtlety before it became a bug: applying persisted widths/visibility during a column rebuild fires the same `sectionResized`/`sectionMoved` signals a *user* action would, which would otherwise cause the rebuild to redundantly re-save the same data back to disk -- worse, hiding a column can report a near-zero width through that signal, which would have silently corrupted the persisted width the next time the rebuild ran. Fixed with a `_suppress_column_signals` guard flag active only during programmatic rebuild.

**Controlled vocabulary for Genre and Language** — both fields switched from freeform text entry to a multi-select checklist (`gui/multi_select_combo.py`, a standard Qt "checkable model + stay-open-on-click" recipe), since a file can genuinely have more than one genre or more than one audio language track. Genre options are TMDB's own movie+TV genre vocabulary merged and deduplicated, chosen specifically so TMDB-imported genre text lands on values this picker also recognizes rather than inventing a separate vocabulary. Language options are a practical ~29-language subset, not the full ~180-entry ISO 639-1 list.

Storage format is unchanged -- still a single comma-separated string in `VideoMetadata`, matching what `genre_tags` already used for freeform text, so neither backend (`mp4_backend.py`/`mkv_backend.py`) needed to change. `core/controlled_vocab.py`'s `parse_multi_value`/`serialize_multi_value` bridge the widget's checked-items set and that string, always serializing in canonical (options-list) order rather than arbitrary set-iteration order, and explicitly preserving any value not in the picker's fixed list (e.g. odd text from a TMDB import) rather than silently dropping it -- though editing and re-saving a field that had such a value will genuinely drop it, an accepted, documented trade-off of switching to a controlled-vocabulary editor. 11 tests, all passing, including a stability check that two differently-constructed sets with identical members always serialize identically.

## 2026-09-02#02 — Rebuilt build_exe.bat against the epub tool's actual proven script

The user uploaded the epub tool's real, working `build_exe.bat` for comparison, surfacing several real gaps in ours beyond the pyinstaller-PATH fix from the previous entry:

- **Missing `cd /d "%~dp0"`** — our script depended on already being in the right working directory; epub's pins itself to its own folder regardless of how it's invoked, so it can't fail to find `requirements.txt`/the spec file from a different cwd.
- **Bare `pip install` instead of `python -m pip install`** — the exact same PATH-mismatch bug class fixed for `pyinstaller` in the previous entry, but missed for `pip` itself; a system with multiple Python installs can have a `pip` on PATH that belongs to a *different* Python than the `python` command resolves to.
- **No `pip install --upgrade pip` first** — an outdated pip can fail to resolve newer PyQt6/PyInstaller wheels; epub upgrades pip before installing anything else.
- **No existence check on the built exe** — epub verifies `dist\epubredactor.exe` actually exists after a "successful" PyInstaller run, catching a class of silent failure where the exit code is 0 but no output was produced.
- **Auto-bumped the version on every build** — removed. Matching epub's design: `bump_version.py` is a separate, deliberate step, so a test/debug build doesn't inflate the official version history every time the script runs.
- **Wrong documented output path** — caught while comparing against epub's `--onefile` flag: `videoredactor.spec`'s `EXE()` call already includes `a.binaries`/`a.zipfiles`/`a.datas` directly with no separate `COLLECT()` step, which is PyInstaller's *onefile* pattern -- meaning the spec has been producing a single `dist/TheVideoRedactor.exe` all along, not the `dist/TheVideoRedactor/TheVideoRedactor.exe` folder structure `BUILD.md` and the previous `build_exe.bat` incorrectly claimed. The spec itself was never wrong; the documentation describing it was. Fixed throughout `BUILD.md` and the script's success message.

Also matched epub's exact parenthesis-escaping convention (`^(...^)`) in the one echo line with literal parentheses in its text, after first writing it with inconsistent escaping (opening paren unescaped, closing paren escaped) and catching the mismatch on review.
